引言
学 Python 的同学，很多都对量化交易感兴趣：抓行情、算指标、写回测、跑策略……一整套下来颇有成就感。但你有没有想过一个问题——大多数量化框架跑完一轮之后，其实并没有变得更聪明。
传统的做法是：把一堆品种、参数、规则丢进同一个回测框架里，用历史数据和统一的评分函数，挑出「相对最优」的那一个。这解决的是「在候选池里选谁」的横向问题，效果不错，但天花板也很明显：它选出来的只是「历史样本内的相对最优」，再跑一次，还是重复同样的打分逻辑，框架本身并没有积累经验。
那么换个思路：真正值得追问的，也许不是「我该选哪个」，而是「系统能不能在运行过程中，持续积累自己的经验」？
本文就带大家用工程化的视角，拆解一个单品种、可自我进化的 AI 交易闭环系统。它不追求一次性覆盖上百种币，而是聚焦一个品种（比如 BTC、黄金或原油的永续合约），把「经验」当作系统运行时真正会改变的核心资产。全文附带 Python 代码案例，并带有中文注释，适合有一定基础的 Python 学习者阅读。
一、两种思路：横向「选优」 vs. 纵向「进化」
先厘清两种工程哲学的区别：
• 横向选优：关注「空间」。在一个搜索空间里横向对比多个候选，选出当下最好的那个。候选池越大越有意义，但每个候选积累的信息往往很浅——一个品种可能只留下几个回测分数，谈不上「个体经验」。
• 纵向进化：关注「时间」。沿着交易时间线，持续记录、复盘、修正每一次决策，让每一个信号、每一笔交易、每一个结果都变成下一次决策可复用的经验。
后者的核心不是「一次选对」，而是构建一个 「决策 → 执行 → 复盘 → 更新」 的闭环。
这里要特别澄清一个容易误解的点：这里说的「进化」不是机器学习意义上的在线训练，也不会更新大模型的权重。 更准确地说，它是外部经验库的持续更新：系统把交易复盘写进数据库，汇总成一份「操作手册」（Playbook），再让下一轮决策去读取这份手册。模型本身不重训，变的只是运行时可用的经验和一小组可调参数。
💡 补充知识：这种模式在业界常被称为「上下文工程」（Context Engineering）或基于外部记忆的智能体（Agent with Memory）。它的优势是成本低、可解释、可回滚；代价是「学到的东西」受限于外部记忆的质量，而非模型能力的真正提升。

二、为什么用「单品种」做闭环实验？
单品种的最大优点是提供了一致的交易上下文。一个市场的波动特征、对新闻的敏感度、假突破的形态、趋势延续的行为，往往各有个性。这些特征一旦混进上百个品种的横向对比里，很容易被平均掉；而持续观察同一个品种，系统才可能反复遇到这些特征，最终把它们沉淀成可复用的规则。
但必须泼一盆冷水：单品种绝不等于更容易学到稳定模式，反而恰恰相反。 单品种系统样本积累慢、统计证据弱，在早期特别容易把短期噪声误当成真实规律。所以更准确的说法是——单品种提供了一个观察「闭环经验如何积累」的稳定环境，但并不能自动保证这些经验可靠。
结论：这套系统在初期应被当作「观察和迭代的对象」，而不是成熟的实盘系统。
三、架构总览：一个闭环，五个阶段
整个系统按 「感知 → 决策 → 执行 → 复盘 → 更新」 五个阶段运转。中间有两条主要的信息通道：技术数据（来自指标快照）和新闻数据（来自搜索与缓存），二者都会送入决策层。
下面逐层拆解。
1. 感知层：把市场翻译成「结构化语言」
系统先计算一组覆盖趋势、动量、波动率、成交量的技术指标（EMA、MACD、RSI、布林带、ATR、KDJ 等）。关键在于：它不会把一堆散乱的数字直接丢给模型，而是组装成一个结构化快照：
# 把各类指标按维度分组，组装成结构化快照
snapshot = {
 "price": price, # 当前价格
 "trend": { # 趋势维度
 "ema_fast": ema_fast, # 快线 EMA
 "ema_slow": ema_slow, # 慢线 EMA
 "macd_hist": hist, # MACD 柱状值
 "macd_hist_rising": hist > hist_prev,# MACD 柱是否在放大
 },
 "momentum": { # 动量维度
 "rsi14": rsi_v, # RSI(14)
 "kdj_k": k_v, # KDJ 的 K 值
 "kdj_d": d_v, # KDJ 的 D 值
 },
 "volatility": { # 波动率维度
 "boll_upper": boll_upper, # 布林带上轨
 "boll_lower": boll_lower, # 布林带下轨
 "atr_pct": atr_v / price * 100, # ATR 占价格百分比
 },
 "volume": { # 成交量维度
 "vol_ratio_to_ma20": vol_ratio, # 相对 20 日均量的比值
 },
}
这一步的意义不是让模型「玄学地读懂市场」，而是把市场状态翻译成模型更容易处理的结构化语言——趋势、动量、波动率、成交量都被显式地放进独立字段里。
新闻层则通过搜索接口抓取相关新闻，去重后存入缓存。它不直接生成交易信号，只提供评估「新闻环境」的原材料。
💡 易错点：很多初学者喜欢把原始数值直接塞进 Prompt，结果模型抓不住重点。结构化 + 语义化字段名（比如 macd_hist_rising 这种布尔字段）能显著提升模型的理解稳定性。

2. 决策层：技术面和新闻面至少不能「打架」
系统把「指标快照 + 近期新闻 + 当前持仓状态 + 当前 Playbook」打包送给大模型，要求它输出一个结构化交易信号，包含：动作、方向、置信度、技术观点、新闻观点、决策理由。
这里有一条硬规则：当技术观点和新闻观点冲突时，系统不允许开仓或加仓。 比如新闻明显偏空、而技术指标提示做多，模型就应该返回 hold 或 close，而不是硬开一个新仓。Prompt 里会写入类似这样的约束：
1. 仅当 technical_view 与 news_view 不冲突时，才返回
 open_long / open_short / add_long / add_short
 （news_view 为中性 / 无数据，或方向与 technical_view 一致）
2. 若 news_view 与 technical_view 方向相反，动作必须是 hold 或 close
3. confidence 必须诚实反映确定性（0-100），
 不要习惯性给高分；把握不足时就给低分
特别注意：「不冲突」只是开仓的必要条件，而非充分条件。 换句话说，技术面和新闻面不打架，不代表系统就一定要交易。模型还得判断信号是否足够强，再输出 open_long、open_short 或 hold。执行层还会额外做一道置信度阈值检查：
# 开仓前的执行层校验：置信度不够就直接放弃
if action in ("open_long", "open_short") and not has_pos:
 if decision["confidence"]  # 置信度低于阈值
 return # 放弃开仓
 open_position(store, decision, ticker, add_mode=False) # 通过则开仓
所以「新闻偏多、技术中性、最终却 hold」是完全符合设计的：新闻有方向性倾向，但技术面确认不足，系统就保持不动。
3. 执行层：参数来自 Playbook，但硬边界永远不动
这套系统与传统「固定参数策略」的一个重要区别是：执行参数不是全部写死在策略逻辑里的。 仓位大小、止损百分比、移动止盈激活阈值、回撤让利阈值等，会尽量从当前版本的 Playbook 里读取。
但这绝不意味着 AI 能随意改参数。初始值、上下限、最大仓位、最大加仓次数、杠杆等边界仍由人工定义，Playbook 只能在这些边界内提供当前取值：
def playbook_param(store, key, config_default, lo, hi):
 # 从当前 Playbook 里取参数，取不到就用默认值
 v = store.get("current_playbook", {}).get("params", {}).get(key, config_default)
 try:
 v = float(v) # 尝试转成浮点数
 except Exception:
 v = config_default # 转换失败则回退到默认值
 return clamp(v, lo, hi) # 关键：无论如何都夹在 [lo, hi] 边界内
每次执行决策时都会读取当前 Playbook，例如止损与基础仓位：
# 读取止损百分比（被夹在人工设定的上下限内）
hard_stop_pct = playbook_param(
 store, "hard_stop_pct",
 HARD_STOP_PCT, HARD_STOP_PCT_MIN, HARD_STOP_PCT_MAX,
)

# 读取基础仓位百分比（同样被夹在上下限内）
base_pos_pct = playbook_param(
 store, "base_pos_pct",
 BASE_POS_PCT, BASE_POS_PCT_FLOOR, BASE_POS_PCT_CEIL,
)
仓位大小也不是固定百分比，而是按「基础仓位 × 当前决策置信度」来算——置信度越低，实际仓位越小：
# 置信度映射到 [0.4, 1.0]，再乘以基础仓位
# 置信度越高，仓位越接近上限
size_pct = base_pos_pct * clamp(decision["confidence"] / 100.0, 0.4, 1.0)
核心思想：不让模型说了算，而是给系统一个可控的参数更新入口。AI 可以「建议」，但最终执行值必须被代码层裁剪（clamp）。
4. 复盘层：只有一笔完整交易结束后，才生成经验
每完成一次「开仓到平仓」的完整交易，系统会把完整的交易上下文（进场理由、方向、盈亏、平仓原因）交给大模型复盘。模型必须输出具体的教训，而不是「操作失误」「行情不好」这类空话。一个好的教训长这样：
RSI 超过 70 后、且新闻环境偏空时追多，容易被套。等回调或直接放弃这笔交易。

复盘结果连同「错误类型分类」一起存入数据库：
schema = {
 "outcome": "win|loss|breakeven", # 结果：盈利 / 亏损 / 打平
 "mistake_type": "none|chased_move|ignored_news_conflict|" # 错误类型：
 "stop_too_tight|stop_too_wide|overleveraged|held_too_long",
 # 无 / 追涨杀跌 / 忽视新闻冲突 / 止损太紧 / 止损太宽 / 杠杆过高 / 持仓过久
 "lesson": "", # 具体教训
 "tags": [""], # 标签
}
关键点：复盘不是每次决策后立刻发生，而是等交易真正结束才发生。 开仓只是记录了一个决策，只有平仓后，系统才知道这笔是赚、是亏还是打平。
5. 更新层：把近期复盘汇总成新的 Playbook
当复盘记录积累到一定数量，或经过固定时间窗口后，系统触发一次 Playbook 更新：读取近期复盘、整体胜率、盈亏统计，然后让大模型生成一份新的经验手册（更新后的「该做 / 该避免」规则 + 对部分参数的调整建议）。
但建议参数绝不无条件采纳，每一个都会被裁剪到人工定义的安全区间：
# 每个可调参数都有人工设定的 (下限, 上限)
bounds = {
 "min_confidence": (MIN_CONFIDENCE_FLOOR, MIN_CONFIDENCE_CEIL),
 "base_pos_pct": (BASE_POS_PCT_FLOOR, BASE_POS_PCT_CEIL),
 "hard_stop_pct": (HARD_STOP_PCT_MIN, HARD_STOP_PCT_MAX),
 "trail_activate_pct": (TRAIL_ACTIVATE_PCT_MIN, TRAIL_ACTIVATE_PCT_MAX),
 "trail_giveback_pct": (TRAIL_GIVEBACK_PCT_MIN, TRAIL_GIVEBACK_PCT_MAX),
}

# 遍历模型建议的参数，逐一裁剪到安全区间后再采纳
for k, (lo, hi) in bounds.items():
 if k in suggested:
 new_params[k] = round(clamp(float(suggested[k]), lo, hi), 4)
裁剪后的参数和新规则被写回数据库，成为下一轮决策使用的当前 Playbook。
这才是这套系统「自我进化」的真正含义：模型权重不变，但外部经验库和可调参数在运行中被更新。 下次模型决策时看到的是新的 Playbook，于是在同一套底层代码上，可能表现出不同的行为倾向。
四、进化 ≠ 失控：闭环内部的硬约束
给系统「自我更新经验」的能力，也带来了明显的风险：如果没有边界，连续几笔亏损可能让模型得出错误教训，反而把参数推向更糟的方向。因此，这套设计有多层约束：
• 第一，AI 不能改代码。 它只能在人工定义的数值区间内微调参数。区间本身由代码或平台设置控制，Playbook 无法越界。
• 第二，硬止损、单品种最大仓位、最大加仓次数在代码层强制执行。 这些属于「硬参数」，与存在 Playbook 里的「软参数」分离——软参数可更新，硬参数不能被 AI 放松。
• 第三，新开仓要求技术面和新闻面至少不冲突。 单一信号源无法独立触发交易。
• 第四，系统默认可运行在「仅通知」模式，让用户先观察信号、复盘和 Playbook 变化，再决定是否开启实盘下单。
最大单品种敞口和最大加仓次数，直接在执行层被检查：
# 按 净值 × 单品种最大仓位比例 × 杠杆 折算出最大可持仓数量
max_qty = equity * MAX_SINGLE_POS_PCT * LEVERAGE / ticker["Last"] / margin

# 若当前持仓 + 本次下单超过上限，则削减到刚好不超限
if cur_qty + qty > max_qty:
 qty = max(0, max_qty - cur_qty)

# 若加仓次数已达上限，直接拒绝
if pos.get("add_count", 0) >= MAX_TOTAL_ADD_COUNT:
 return
底层原则很简单：闭环可以调整「怎样做得更好」，但不能放松「允许承担多少风险」这条底线。
五、它离「成熟的持续学习系统」还有多远？
必须说清楚：这套系统离真正成熟的持续学习系统还很远。 核心差异可以一句话概括：成熟的持续学习系统会追问「这条新教训在系统从未见过的数据上是否依然成立？」，而当前这个闭环，本质上主要是在总结已经发生的、数量有限的交易。

参数变更依据用显著性检验、置信区间、严格回测更多依赖近期复盘和模型生成的总结
尽管如此，它并非没有价值。它的价值在于：把交易中那些本来靠人工完成的活动——记录、复盘、总结、更新、复用经验——结构化了。 以前这些教训散落在个人笔记、聊天记录或主观记忆里，现在被写进数据库支撑的 Playbook，成为下一次决策真正能读取的上下文。
但这也意味着早期需要极度谨慎：系统产出的一条教训，可能反映真实规律，也可能只是短期噪声。尤其在单品种、低频交易、样本稀薄的情况下，任何「进化结果」都不该被太快信任。
⚠️ 风险提示：本文仅为策略设计思路的技术探讨，不构成任何投资建议。加密货币及衍生品交易风险极高，请务必审慎评估自身风险承受能力。

总结
Loop Engineer 这套思路，最吸引人的地方不是「跑得越久越准」的承诺，而是它把「变得更好」这件事，从原本需要人工调参、重新部署策略的动作，变成了系统正常运行中就能被记录、被复盘、被更新的一部分。
对学 Python 的同学，这套设计有几个值得反复咀嚼的工程要点：
1. 结构化优于原始数据：把指标组装成带语义的快照，比堆一堆数字更利于决策层理解。
2. 软硬参数分离：可进化的软参数放 Playbook，不可放松的硬边界（止损、最大仓位、加仓次数）写死在代码层，并用 clamp 兜底。
3. 闭环而非单次：决策 → 执行 → 复盘 → 更新，让每一笔交易都能沉淀成下一次的上下文。
4. 进化不等于放权：给系统一个「可控的更新入口」，AI 只能建议、代码层负责裁剪。
5. 保持敬畏：改进不会自动发生，样本太小时同样可能学到噪声、向错误方向漂移。人工观察每一次 Playbook 更新，依然不可或缺。
更稳妥的做法是：先用「仅通知」模式跑一段时间，观察信号、复盘和 Playbook 演化的质量，再决定是否进入小仓位实盘。搭好闭环只是第一步，它能否真正积累有用经验，最终必须靠足够的时间、足够的交易样本和严格的风控来检验。
